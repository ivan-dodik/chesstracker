# Отчёт по проекту Chess Tracker

## 1. Введение

**Chess Tracker** — веб-приложение для управления шахматными турнирами: регистрация игроков, проведение турниров, запись партий, отслеживание рейтингов, статистика, уведомления в реальном времени и Telegram-бот.

**Стек:** Python 3.12 + FastAPI + PostgreSQL + Jinja2/HTMX/Alpine.js + Docker Compose.

**AI-инструменты:** Cline (плагином к VS Code), deepseek/deepseek-v4-flash и xiaomi/mimo-v2.5 через OpenRouter. Агент использовался в двух режимах: **Plan** (анализ, уточнение) и **Act** (реализация).

---

## 2. Организация работы с AI-агентом

Для сохранения контекста между задачами использовал штатный механизм Cline: memory bank - набор MD файлов с основной информацией о проекте. Обновлялся согласно правилу (самописному)  в конце каждой задачи, перед коммитом. Периодически вручную просил агент обновить всю документацию.

### Memory Bank

Набор Markdown-файлов, которые AI читает в начале каждой сессии, чтобы восстановить контекст:

* 6 стандартных для Cline файлов: описание проекта, цели, текущий статус, архитектура, технологии, прогресс - определены в типовом правиле из документации
* ~30 модульных файлов в 7 категориях (backend, frontend, тесты, инфраструктура, конфиги, Telegram-бот, мета) - попросил агент подготовить для ускорения навигации после того как заметил что он грепает каждый раз заново. Впрочем он не всегда обращался к ним.
* index.md с quick-lookup таблицей - теоретически агент должен был находить нужный файл по индексу, на практике, кмк, он не всегда это делал.

### Правила (.clinerules/)

Основная "обвязка", определяет ход разработки:

* `git_commit.md` - авто-коммит и пуш после каждой задачи (там же обновление документации).
* `report.md` - вести отчёт параллельно с разработкой (он вышел слишком "машинным", пришлось переделывать вручуную).
* `update_prompts.md` - сохранять каждый промпт (постоянно соскакивало).
* `implementation_plan.md` - отслеживать прогресс по чекмаркам.
* `tdd.md` - использовать Test-Driven Development (по опыту сильно помогает).
* `skills-usage.md` - маппинг задач на скиллы (добавил после установки скиллов).

### Агентские скиллы

Попросил агента поискать самому и установить со skills.sh - съело кучу токенов и поставил лишнее, пришлось потом чистить. Самые полезные, кмк - TDD, caveman (в PR у них лежит русификация), тестирование веб-приложений, диагностика проблем.

### MCP-серверы

* Context7 MCP - встроенный в CLine - поиск актуальной документации по библиотекам.
* Browser Tools MCP - верификация фронтенда в реальном Chrome - работает так себе, год не обновляется.
* Playwright MCP - браузерная автоматизация (открытие страниц, скриншоты, клики, проверка консоли/сети) - незаменим для E2E тестов.
* Filesystem MCP - расширенный доступ к файловой системе - особо не заметил его использования.

## 3. Примеры промптов

### Промпт 1. Создание плана реализации

> «Проанализируй задание и напиши подробный пошаговый план для Cline по реализации проекта. Шаги должны быть небольшими, после каждого майлстоуна — коммит и обновление memory-bank.»

**Результат:** Создан `IMPLEMENTATION_PLAN.md` (11 майлстоунов, ~80 шагов). Агент задал уточняющие вопросы (webhook vs polling, хранение JWT, pre-commit hook), что помогло зафиксировать архитектурные решения на старте.

### Промпт 2. Исправление пустых страниц

> «Страницы турнира и игрока пустые, данные не загружаются.»

**Диагностика агента:** проверил БД → API → HTML → JavaScript. Обнаружил, что `fetch()` в Alpine.js не передаёт `Authorization` header (HTMX добавляет автоматически, а Alpine — нет). Исправил 14 fetch-вызовов за одно действие. 

### Промпт 3. Запрос code review

> Агент запустил параллельных subagent'ов для анализа всех исходных файлов.

**Результат:** 22 проблемы (5 critical: default SECRET_KEY, N+1 запросы, CSV без лимита), исправлены 21 из 22. Создан `CODE_REVIEW.md` и `SECURITY_AUDIT.md`.

## 4. Ключевые проблемы и решения

### Проблемы с фронтендом

Основные, которые потребовали дополнительных промптов: Jinja2 cache error, некорректная инициализация Alpine.js. Потребовали смены LLM, использования MCP, скиллов по диагностике.

### Нерегулярное обновление документации

Агент периодически забывал обновлять файлы PROMPTS.md, CHANGES.md, REPORT.md. Несколько раз переделывал правила, указывал дополнительные, требовал добавления в план (в этом случае работало более менее). Но всё равно приходилось периодически напоминать ему, особенно если это были разовые задачи.

### Автотесты не ловили проблему с фактической работой фронта

Автотесты проходили, но на страницах турнира и игрока были прочерки и бесконечные спиннеры и т.д. Решилось добавлением E2E тестов через Playwright. Вывод - т.к. агент не знает, что должно быть в итоге - всегда требовать создания Е2Е тестов!

## 5. Выводы (от ИИ)

Работа над проектом показала:

1. **AI эффективен для генерации кода**, но требует контроля и уточняющих промптов. Без обратной связи агент генерирует работающий, но не всегда правильный код.

2. **Инфраструктура вокруг агента — ключ к качеству.** Memory Bank, правила, скиллы, MCP-серверы — всё это нужно не для «красоты», а для того, чтобы AI работал последовательно и не забывал важные шаги.

3. **Тесты не заменяют проверку в реальном браузере.** API-тесты проверяют бэкенд, но не JavaScript. Playwright MCP оказался незаменимым инструментом.

4. **Правила должны быть согласованы.** Противоречия в инструкциях приводят к тому, что агент выбирает «удобное» поведение, а не правильное.

5. **Чёткий промпт экономит часы.** Размытый промпт создаёт проблемы, которые исправлять дольше, чем формулировать задачу с самого начала.
