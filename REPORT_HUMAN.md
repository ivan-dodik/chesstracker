# Отчёт о процессе разработки Chess Tracker

## 1. Введение

**Chess Tracker** — веб-приложение для шахматных турниров и рейтингов. Пользователи могут регистрировать игроков, проводить турниры, записывать партии с результатами, отслеживать рейтинги и статистику. Есть дашборд с графиками, head-to-head статистика, избранное, экспорт/импорт CSV, SSE-уведомления в реальном времени и Telegram-бот.

**Стек:** Python 3.12, FastAPI, PostgreSQL, Jinja2 + HTMX + Alpine.js, Docker Compose, Alembic, uv, ruff.

**Единственный AI-инструмент:** Cline — расширение для VS Code, работающее в двух режимах: **Plan Mode** (анализ, планирование) и **Act Mode** (реализация). Все файлы проекта — код, документация, тесты, конфигурация — сгенерированы AI-агентом. Моя роль — формулирование промптов и контроль результата.

## 2. Обвязка и инфраструктура AI-агента

Одна из главных сложностей работы с AI-агентом — **потеря контекста между сессиями**. При каждом перезапуске Cline «забывает» всё, что было до этого. Чтобы обеспечить непрерывность разработки, была создана обширная инфраструктура вокруг агента.

### Memory Bank — «память» между сессиями

Memory Bank — это набор Markdown-файлов, которые AI читает в начале каждой сессии, чтобы понять текущее состояние проекта.

- **6 core-файлов:** projectbrief (описание проекта), productContext (цели и проблемы), activeContext (текущая работа), systemPatterns (архитектура), techContext (технологии), progress (что сделано)
- **~30 модульных файлов** в 7 категориях: backend (API, модели, сервисы, Docker), frontend (шаблоны, JS, CSS), testing, infrastructure, config, meta, telegram-bot
- **index.md** с quick-lookup таблицей — агент может за секунду найти нужный файл, не читая исходный код

### Правила (.clinerules/) — 9 файлов, управляющих поведением агента

Без правил AI работает хаотично: забывает коммитить, не обновляет документацию, делает лишние действия. Правила структурируют процесс:

| Правило | Что делает |
|---------|-----------|
| `git_commit.md` | Авто-коммит и пуш после каждой задачи, формат сообщений |
| `report.md` | Параллельное ведение отчёта (не в конце!) |
| `update_prompts.md` | Каждый промпт сохраняется в PROMPTS.md |
| `implementation_plan.md` | Отслеживание прогресса по чекмакам |
| `memory-bank.md` | Обновление Memory Bank после изменений |
| `tdd.md` | Test-driven development, Red-Green-Refactor |
| `skills-usage.md` | Маппинг задач → скиллов, caveman-режим |

### Агентские скиллы — 32 специализированных инструкции

Скиллы — это готовые наборы инструкций для типичных задач. При получении задачи агент автоматически выбирает нужный скилл:

- **Python/FastAPI** — best practices для API и async-операций
- **PostgreSQL** — проектирование схем и оптимизация запросов
- **Docker** — контейнеризация и Docker Compose
- **HTMX / Alpine.js** — фронтенд без тяжёлых фреймворков
- **TDD** — тестирование через Red-Green-Refactor
- **Code Review** — аудит безопасности и производительности
- **Webapp Testing** — E2E-тесты через Playwright
- **Brainstorming / Design** — проектирование интерфейсов

Каталог скиллов (`skills-index.md`) содержит триггеры для автоматического выбора. Например, при запросе «исправь ошибку на странице» агент активирует скилл `diagnose`, а при «напиши тесты» — `tdd`.

### MCP-серверы — внешние инструменты

MCP (Model Context Protocol) — протокол для подключения внешних инструментов к агенту:

- **Playwright MCP** — браузерная автоматизация. Агент может открыть страницу в реальном Chrome, сделать скриншот, кликнуть на элемент, заполнить форму, проверить консоль на ошибки. Использовалось для верификации логина, проверки рендеринга страниц, аудита доступности.
- **Filesystem MCP** — расширенный доступ к файловой системе (чтение, запись, поиск, дерево каталогов)
- **Context7 MCP** — поиск актуальной документации по библиотекам (FastAPI, SQLAlchemy, Jinja2) прямо во время разработки
- **Sequential Thinking MCP** — цепочка рассуждений для сложных архитектурных задач

### Документация проекта

Помимо кода, AI вёл обширную документацию:

- `IMPLEMENTATION_PLAN.md` — 17 майлстоунов с ~80 шагами и чекмаками
- `ARCHITECTURE.md` — ERD, диаграмма API, описание стека
- `CHANGES.md` — история всех изменений (дата, файлы, описание)
- `PROMPTS.md` — каждый промпт сохранён (~1500 строк)
- `BUGS.md`, `CODE_REVIEW.md`, `SECURITY_AUDIT.md` — отчёты по проблемам

## 3. Как я работал с AI — процесс

Разработкой Chess Tracker управлял AI-агент Cline. Мой процесс выглядел так:

1. **Формулирую промпт** — описываю задачу на естественном языке
2. **AI анализирует** (Plan Mode) — читает файлы, задаёт уточняющие вопросы
3. **AI представляет план** — конкретные шаги, затронутые файлы
4. **Переключаю в Act Mode** — AI реализует план
5. **AI коммитит и обновляет документацию** — автоматически по правилам

За проект было отправлено ~50 промптов. Вот характерные примеры:

**Планирование (один промпт → план на весь проект):**
> «Проанализируй задание на проект и напиши подробный пошаговый план для агента по его реализации. Шаги должны быть небольшими. После каждого майлстоуна обновляй memory-bank.»

Результат: `IMPLEMENTATION_PLAN.md` — 11 майлстоунов, ~80 шагов, вопросы по архитектурным решениям (webhook vs polling, JWT storage, pre-commit hook).

**Исправление бага ( AI нашёл корневую причину):**
> «Страницы турнира и игрока пустые, данные не загружаются.»

AI провёл диагностику: проверил БД → API → HTML → JavaScript → обнаружил, что `fetch()` в Alpine.js не передавал `Authorization` header (HTMX добавлял автоматически, а Alpine — нет). Исправил 14 fetch-вызовов за одно действие.

**Code review через AI:**
> Агент запустил параллельных subagent'ов для анализа всех исходных файлов.

Результат: 22 проблемы (5 critical: default SECRET_KEY, N+1 запросы, CSV без лимита), исправлены 21 из 22.

## 4. Что получилось хорошо

**Генерация boilerplate-кода.** Один промпт → полная архитектура, 7 SQLAlchemy-моделей, CRUD-эндпоинты, тесты. AI справился с созданием ~2000 строк кода за несколько сессий.

**Автоматизация рутины.** Правила в `.clinerules/` заставляли агента коммитить после каждого этапа, обновлять документацию, запускать ruff и тесты. Без этого пришлось бы делать вручную.

**E2E-тестирование через Playwright MCP.** Агент мог открыть реальный Chrome, залогиниться под admin, проверить консоль на ошибки, сделать скриншот, провести аудит доступности — всё автоматически.

**Code review и безопасность.** AI нашёл проблемы, которые я бы не заметил: default SECRET_KEY, CORS `*`, N+1 запросы, CSV-импорт без лимита. Все исправлены.

**Модульная документация для агента.** Создание ~30 модульных файлов в Memory Bank с quick-lookup таблицей решило проблему «зависания» агента на чтении исходников при переключении между задачами.

## 5. Ключевые проблемы

### Правила конфликтовали друг с другом

Правило `report.md` предписывало вести отчёт «параллельно с работой», но в `IMPLEMENTATION_PLAN.md` создание отчёта было запланировано только в последнем майлстоуне. Агент следовал плану и не создавал файл. Пришлось вручную исправлять план и правило.

**Урок:** Все правила агента должны быть согласованы. Противоречия в инструкциях приводят к непредсказуемому поведению.

### HTMX + Alpine.js — конфликт инициализации

При AJAX-навигации (hx-boost) скрипты шаблонов добавляли listener на событие `alpine:init`, но это событие срабатывает **только один раз** при старте Alpine.js. При навигации через HTMX event не повторялся → компоненты не регистрировались → страницы пустые.

**Решение:** Вызов `Alpine.data()` напрямую (без обёртки `alpine:init`) + `Alpine.initTree()` в обработчике `htmx:afterSwap`.

### Тесты не покрывали фронтенд

148 тестов проходили успешно, но на страницах турнира и игрока были прочерки и бесконечные спиннеры. Причина: Alpine.js компоненты использовали `fetch()` без `Authorization` header. Тесты передавали токен явно и не проверяли клиентский JavaScript.

**Урок:** API-тесты ≠ проверка фронтенда. Нужны E2E-тесты (Playwright) для реальной проверки работы в браузере.

### AI забывал обновить документацию

Несмотря на правила, агент систематически пропускал обновление CHANGES.md, PROMPTS.md и REPORT.md. Только ручная проверка перед коммитом выявляла пропуски.

**Решение:** Усиление правил — категоричные формулировки вместо условных, добавление явных чекмаков в каждый майлстоун.

### Jinja2 + Starlette — несовместимость версий

При загрузке страницы HTTP 500: `TypeError: unhashable type: 'dict'` в Jinja2-кэше. Starlette передаёт dict как глобальную переменную, а Jinja2 ≥3.1.x использует LRUCache с изменённым API.

**Решение:** Кастомный `Environment` с `cache_size=0`, обход стандартного `Jinja2Templates`.

## 6. Выводы

Работа с AI-агентом над проектом длиной ~2000 строк кода показала:

1. **AI эффективен для генерации кода**, но требует постоянного контроля и уточняющих промптов. Без обратной связи агент генерирует работающий, но не всегда правильный код.

2. **Инфраструктура вокруг агента — ключ к качеству.** Memory Bank, правила, скиллы, документация — всё это нужно не для «красоты», а для того, чтобы AI мог работать последовательно и не забывал важные шаги.

3. **AI-тесты не заменяют проверку в реальном браузере.** Тесты проверяют API, но не проверяют, что JavaScript работает правильно. Playwright MCP оказался незаменимым инструментом для верификации.

4. **Правила должны быть согласованы.** Противоречия в инструкциях приводят к тому, что агент выбирает «удобное» поведение, а не правильное.

5. **Промпты — это основной инструмент разработчика.** Чётко сформулированный промпт экономит время; размытый — создаёт проблемы, которые потом исправлять дольше.
