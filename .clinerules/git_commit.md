# Правила автоматического коммита и пуша

При завершении задачи (перед вызовом `attempt_completion`) агент **обязан** выполнить коммит всех изменений и пуш в основной репозиторий.

## Процедура

1. **Проверить статус репозитория** — выполнить `git status`, чтобы увидеть все изменённые, новые и удалённые файлы.

2. **Сгенерировать описание коммита** — на основе выполненных изменений составить осмысленное сообщение на русском или английском языке (в зависимости от контекста задачи). Формат:
   ```
   <тип>: <краткое описание>
   
   <подробное описание изменений, если необходимо>
   ```
   Типы коммитов:
   - `feat` — новая функциональность
   - `fix` — исправление ошибки
   - `docs` — документация
   - `chore` — обслуживание (настройка, зависимости, CI)
   - `refactor` — рефакторинг без изменения функциональности
   - `test` — тесты
   - `style` — форматирование, стили

3. **Добавить файлы в коммит**:
   - `git add -A` — добавить все изменения (включая новые файлы)
   - ИЛИ точечное добавление, если нужно исключить какие-то файлы

4. **Выполнить коммит**:
   ```
   git commit -m "<сгенерированное сообщение>"
   ```

5. **Запушить изменения**:
   ```
   git push
   ```

## Когда выполнять

- **Всегда** перед `attempt_completion`, если были внесены изменения в файлы проекта.
- Если изменений не было (например, задача — только прочитать информацию) — коммит не требуется.

## Исключения

- Если `git push` завершается ошибкой (нет удалённого репозитория, нет прав) — выполнить коммит локально и сообщить пользователю о проблеме с пушем.
- Если пользователь явно попросил **не** коммитить — пропустить шаг.

## Важно

- Коммит должен быть **атомарным**: одна задача — один коммит.
- Сообщение коммита должно отражать **суть изменений**, а не быть формальным.
- Не коммитить служебные файлы, перечисленные в `.gitignore`.
