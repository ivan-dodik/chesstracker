# Правила ведения REPORT.md

REPORT.md — это дневник разработки проекта. Он будет оцениваться преподавателем.
Заполняется **параллельно** с работой, а не в конце.

## Структура

```markdown
# Отчёт по проекту Chess Tracker

## Использованные AI-инструменты
- Перечислить все AI-инструменты, использованные в проекте (Cline, ChatGPT, Copilot и т.д.)
- Кратко описать, для чего каждый применялся

## Примеры промптов
Привести минимум один показательный пример промпта с разбором:

### Пример 1: [Название этапа]
- **Что хотели получить:** описание задачи
- **Промпт:** (текст промпта)
- **Результат:** что получили, что пришлось дорабатывать
- **Вывод:** удачный/неудачный, почему

## Ключевые проблемы и решения
Хронология основных трудностей и как они были решены:

### [Дата] — [Проблема]
- **Суть:** что пошло не так
- **Причина:** почему это произошло
- **Решение:** как исправили
- **Результат:** сработало или нет

## Удачные и неудачные шаги
- ✅ **Удачно:** что получилось хорошо, какие решения ускорили разработку
- ❌ **Неудачно:** что пошло не по плану, что стоило сделать иначе

## История работы
Формат: дата / время — краткое описание шага
```

## Правила заполнения

1. **После каждого значимого шага** (создание файлов, запуск тестов, Docker, CI) — добавить запись в раздел «История работы»
2. **При возникновении проблемы** — сразу зафиксировать в «Ключевые проблемы и решения», пока детали свежи
3. **Перед attempt_completion** — проверить, что REPORT.md отражает все ключевые события этапа
4. **Не откладывать** — запись «потом» не будет сделана
5. **Быть честным** — неудачные шаги ценнее для отчёта, чем удачные

Читай этот файл в начале каждой сессии, чтобы не забыть обновлять REPORT.md.
